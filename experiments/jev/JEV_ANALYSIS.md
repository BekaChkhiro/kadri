# Jev და „კადრი“ — გამოყენების შეფასება

2026-10-17 · დოკუმენტაციისა და კოდის მიმოხილვა; API გამოძახებები: **0**. ქვემოთ არქიტექტურა, JSON მაგალითები, ბიუჯეტი და მიღების კრიტერიუმები **შემოთავაზებებია**, არა განხორციელებული ინტეგრაცია ან გაზომილი შედეგები.

**რეკომენდაცია:** პირველი ექსპერიმენტი იყოს ქართული მითითების უკვე აღმოჩენილი ნაწილის ID-ზე მიბმა. Jev შეიძლება გამოდგეს იაფ სემანტიკურ გადამრთველად; AR ტრეკინგი, გეომეტრია და დაუყოვნებელი გაფრთხილება დარჩეს მოწყობილობაზე. Vision/Box უკვე არსებობს ექსპერიმენტულად, მაგრამ Astra-ს ჩანაცვლების საფუძველი ჯერ არ გვაქვს.

## 1. რა შეიცვალა და რას გვთავაზობს API

2026-09-15-ის [განცხადება](https://typesafe.ai/blog/introducing-system-one-models-and-jev) Jev-ს System One მოდელად, early access-ითა და waitlist-ით წარადგენდა. **70–500 მს, კალიბრაცია და დიდი მოდელების მსგავსი ინტელექტი კომპანიის მტკიცებებია**, არა „კადრში“ გაზომილი შედეგები; თავადვე აღნიშნავს აშშ-ის დასავლეთ სანაპიროდან ტესტირებას. ამჟამინდელი [Quick start](https://docs.typesafe.ai/introduction/quickstart) პირდაპირ console/API key-ს უთითებს; რეგისტრაცია არ შეგვიმოწმებია და ისტორიული waitlist მიმდინარე აუცილებელ პირობად არ უნდა მივიჩნიოთ.

**„სურათი ჯერ არა“ უკვე მოძველებულია:** [Images](https://docs.typesafe.ai/images) Jev 1.13/1.14-ში სურათებს აღწერს, ხოლო [Box](https://docs.typesafe.ai/primitives/box) მოითხოვს `jev-1.14.0` ან `jev-preview`-ს და აბრუნებს `top/bottom/left/right` კოორდინატებს 0–1-ში, confidence-თან ერთად. ორივეს სჭირდება `TypeSafe-Danger-Zone-Images: true`. კომპანია მათ production-ისთვის მოუმზადებლად მიიჩნევს; ფორმატი, ლიმიტები და ხარისხი შეიძლება შეიცვალოს. `assets` შეიცავს PNG/JPEG-ს base64-ით ან multipart-ით, ხოლო `state` — მის reference-ს. ეს უკვე პროტოტიპირების შესაძლებლობაა, არა მხოლოდ roadmap; production-ready ვადა ვერ დადასტურდა. Models-ის ძირითად ცხრილში ჯერ ისევ Text წერია — ექსპერიმენტული გამონაკლისი სპეციალურ გვერდებზეა.

ტექსტური [API კონტრაქტი](https://docs.typesafe.ai/api): `POST https://api.typesafe.ai/v1/systemone`, Bearer key; body — `model`, `state` (string/object/array), `questions` map. ეს Jev-ის კითხვების ფორმატია, არა თავისუფალი JSON Schema. `choice` იღებს ≤255 დასახელებულ ვარიანტს; `score` — 2–10 დალაგებულ დონეს; `noul` — დიახ/არას ალბათობას 0–1-ში, **არა boolean-ს**. Choice/Score აბრუნებს ალბათობებსა და confidence-ს; Noul-ს ცალკე confidence არ აქვს. [Confidence](https://docs.typesafe.ai/confidence) განაწილებიდან გამოთვლილი მაჩვენებელია და ჩვენი ქართული ამოცანის სისწორის გარანტიას არ ნიშნავს.

## 2. აპის შესაბამისობა და შვიდი კანდიდატი

[პროდუქტის brief](../../Camera/brief.md) მოითხოვს ქართულ realtime კამერას და AR შეკეთებას; [repair.tsx](../../Camera/artboards/repair.tsx) და [ethernet.tsx](../../Camera/artboards/ethernet.tsx) აჩვენებს ნაბიჯებს, focus-სა და avoid-ს. [variant_c.py](../som-test/variant_c.py) ნაწილების შემდეგ ნაბიჯებს stream-ით იღებს; `assign_ids` ცენტრების დალაგებას იყენებს. [realism.py](../som-test/realism.py)-ის matching გეომეტრიულია: **რეალური ARKit/ARCore anchor ინტეგრაცია ამ ფაილებით არ დასტურდება**, ის მიზნობრივი არქიტექტურაა. [REALISM.md](../som-test/REALISM.md)-ში Astra first-box p50 არის 6.78 წმ stress-ში და 7.49 წმ tracking-ში; ≤5 წმ მიზანი ვერ შესრულდა. სინთეზური კადრები mobile ვალიდაცია არ არის.

ქვემოთ `state`/`question` წყვილები საკუთარი დიზაინის მაგალითებია. მათი სრული body არის `{"model":"jev-1.13.0","state":STATE,"questions":{"decision":QUESTION}}`, [API ფორმატის](https://docs.typesafe.ai/api) მიხედვით. ID-ები ერთ სცენას ეკუთვნის; ტრეკერის დამატებითი სიგნალები ჰიპოთეზურია, არსებული `plan.json` მათ არ შეიცავს. თითო **2,000 input-token** მოთხოვნა ღირს დაახლოებით **$0.000084**; 1,000 ასეთი მოთხოვნა — **$0.084**, ინფრასტრუქტურის გარეშე ([ტარიფი](https://docs.typesafe.ai/models), ჩვენი არითმეტიკა). ქვემოთ „ერთი Jev-call“ ამ საორიენტაციო ხარჯს ნიშნავს; ზომა რეალურად უნდა გაიზომოს.

**1. ხმოვანი/ტექსტური მითითება → ID — საუკეთესო საწყისი კანდიდატი.**

`state = {"utterance":"მარჯვენა ქანჩი მაჩვენე","parts":{"p1":"ზედა ქანჩი","p4":"მარჯვენა ქანჩი, წვეთებით"},"visible":["p1","p4"]}`

`question = {"type":"choice","instructions":"აირჩიე მომხმარებლის მიერ დასახელებული ხილული ნაწილი; გაურკვევლობაზე unknown.","criteria":{"p1":"ზედა ქანჩი","p4":"მარჯვენა ქანჩი","unknown":"არ ჩანს ან ერთმნიშვნელოვნად ვერ განისაზღვრება"}}`

Backend იძახებს დასრულებული ტექსტის/ASR ტრანსკრიპტის შემდეგ. შეიძლება ჩაანაცვლოს **ცალკე Astra სემანტიკური lookup**, თუ მას დავამატებდით; არსებული ორსაფეხურიანი run ავტომატურად არ მცირდება. შეხებით არჩევას მოდელი არ სჭირდება. სარგებელი: ერთი მცირე call დიდი ტექსტური lookup-ის ნაცვლად; დროის სხვაობა ჯერ გასაზომია. „ეს“ pointing-ს გარეშე unknown უნდა იყოს. ხმა ჯერ ASR-მ უნდა გადააქციოს ტექსტად.

**2. „ნაბიჯი შესრულდა?“ — მხოლოდ დამხმარე შეფასება.**

`state = {"step":"მოუშვი p4","events":["p4 ბრუნვა დაფიქსირდა"],"tracking":"stable","user_confirmed":false,"detached":"unknown"}`

`question = {"type":"choice","instructions":"არსებული მტკიცებულება ადასტურებს p4-ის მოშვებას? ბრუნვა მარტო დასრულება არ არის.","criteria":{"done":"დასრულება დადასტურებულია","not_done":"დაუსრულებლობა დადასტურებულია","unknown":"მტკიცებულება არასაკმარისია"}}`

ნაბიჯის controller/backend იძახებს დასრულების კანდიდატ მოვლენაზე, არა ყოველ frame-ზე. შეიძლება ჩაანაცვლოს დამატებითი ტექსტური Astra შეფასება, მაგრამ anchor-ის მოძრაობა ქანჩის მოშვებას, ნაკადის შეწყვეტას ან სწორი ძალით მოჭერას არ ამტკიცებს. წესებსა და მომხმარებლის დასტურთან შედარებით ემატება ერთი call-ის დრო/ხარჯი; უცნობი სენსორული ფაქტი Jev-ით ვერ შეივსება. ავტომატური წინსვლა არ ვურჩევთ.

**3. Intent routing — გამოსადეგი მხოლოდ ბუნდოვანი ტექსტისთვის.**

`state = {"utterance":"ამ ეტიკეტზე რა წერია?","selected_id":"p4","mode":"camera"}`

`question = {"type":"choice","instructions":"რომელი დამმუშავებელი სჭირდება მოთხოვნას?","criteria":{"repair":"შეკეთების ნაბიჯები","identify":"ობიექტის ახსნა","translate":"წარწერის წაკითხვა/თარგმნა","unknown":"გაურკვეველი"}}`

Backend — ახალი გამოთქმისას, ID-მიბმასთან ერთ მოთხოვნაში თუ კითხვები დამოუკიდებელია. ანაცვლებს შესაძლო Astra router-ს ან რთულ ტექსტურ წესებს. აშკარა UI რეჟიმისთვის წესები იაფი და სწრაფია; აქ Jev დამატებითი call იქნება. თარგმნის გზის არჩევა თავად თარგმანს არ ქმნის.

**4. ხელი/კამერა avoid ნაწილთან — მთავარ guard-ად არ ვარგა.**

`state = {"avoid":["p1"],"hand_overlap_ids":["p1"],"camera_target":"p1","tracking":"stable"}`

`question = {"type":"noul","instructions":"ფიქსირდება ხელის გადაფარვა avoid ნაწილთან? კამერის მიმართვა შეხებად არ ჩათვალო."}`

ეს არის შესაფასებელი, მაგრამ **არარეკომენდებული** Jev-call: on-device controller-ს შეუძლია უკვე დათვლილი სიების თანაკვეთა მაშინვე შეამოწმოს. ანაცვლებს წესს, ხარჯისა და ქსელური დაყოვნების დამატებით, სარგებლის გარეშე. Hand-overlap-ის მისაღებად ჯერ ხელის detector/გეომეტრიაა საჭირო; AR anchor მარტო ხელს არ ხედავს. Cloud შეფასება მხოლოდ შემდგომი აუდიტისთვის შეიძლება.

**5. Astra-ს ხელახალი გამოძახების გადაწყვეტილება — პირობითად გამოსადეგი.**

`state = {"tracking":"relocalized","new_object_event":true,"user":"ახლა სხვა ონკანს ვაკეთებ","plan_scene":"sink"}`

`question = {"type":"choice","instructions":"სჭირდება მოთხოვნას ახალი სცენის გაგება?","criteria":{"reuse":"იგივე სცენა და მიზანი","refresh":"შეცვლილი ობიექტი ან მიზანი","ask":"არასაკმარისი მტკიცებულება"}}`

Backend — მნიშვნელოვანი მოვლენისას, debounce-ით. სემანტიკური მიზნის ცვლილებაზე შეიძლება აარიდოს ზედმეტი დიდი call; tracker დაკარგვა/დროის ზღვარი ადგილობრივ წესებს უნდა ეკუთვნოდეს. დაზოგვა: `აცილებული Astra-call-ების ფასი − Jev-call-ების ფასი`; რაოდენობა ჯერ უცნობია. პირველი აღმოჩენის წინ gate-ის დამატება მხოლოდ აყოვნებს მას.

**6. ძველი/ახალი parts matching — მხოლოდ სადავო წყვილებისთვის.**

`state = {"old":{"id":"a17","label":"მარჯვენა ქანჩი"},"new":{"p3":"ზედა ქანჩი","p4":"მარჯვენა პლასტმასის ქანჩი"},"geometry_candidates":["p3","p4"]}`

`question = {"type":"choice","instructions":"რომელი ახალი ჩანაწერი შეესაბამება old ნაწილს?","criteria":{"p3":"ზედა ქანჩი","p4":"მარჯვენა პლასტმასის ქანჩი","unknown":"იდენტობა ვერ დასტურდება"}}`

Backend — ხელახალი detection-ის შემდეგ, გეომეტრიული shortlist-ის ბუნდოვან წყვილებზე. არსებული IoU/anchor matching-ის ჩანაცვლება არ ღირს; ეს ახალი დამატებითი სემანტიკური შეფასებაა, თითო call-ის ხარჯით. მსგავს ნაწილებს ტექსტი ვერ განასხვავებს გარანტირებულად. დამოუკიდებელმა პასუხებმა ერთი ID ორჯერ შეიძლება აირჩიოს: საბოლოო one-to-one assignment და კონფლიქტის უარყოფა კოდს ეკუთვნის.

**7. გეგმის guardrail — ფორმალური წესები კოდში, სემანტიკა სურვილისამებრ.**

`state = {"step":{"text":"მოუშვი ზედა ქანჩი","focus":["p4"]},"parts":{"p4":"მარჯვენა ქანჩი"},"visible":["p4"]}`

`question = {"type":"noul","instructions":"ეწინააღმდეგება ნაბიჯის ტექსტში დასახელებული მდებარეობა focus ნაწილის label-ს?"}`

Backend — streamed ნაბიჯის გამოტანის წინ/ფონურ შემოწმებაზე. ტექსტი↔label წინააღმდეგობისთვის შეიძლება ჩაანაცვლოს ცალკე Astra reviewer; ემატება ერთი Jev-call. `focus ⊆ visible`, უცნობი ID, focus/avoid კონფლიქტი კოდით შემოწმდეს — ამაში მოდელის სარგებელი ნულოვანია. არასწორად ამოცნობილი label-ის ჭეშმარიტებას ტექსტური reviewer ვერ დაადგენს.

## 3. არქიტექტურა, latency და შეზღუდვები

შემოთავაზებული მიმდევრობა:

```text
კამერა → პირველი Astra parts/box → SAM2 → ტელეფონის მუდმივი ID/anchor
                   └→ Astra ნაბიჯების stream → ლოკალური ვალიდაცია → AR UI
AR/ხელის detector → ადგილობრივი წესები → დაუყოვნებელი highlight/გაფრთხილება
ტექსტი/ASR + მინიმალური state → backend → Jev → ID/route/refresh შეთავაზება
                                            └→ დაბალი სანდოობა: კითხვა/დასტური
```

ეს დიზაინი პირველი box-ის არსებულ ~7 წამს **არ ამცირებს**. მიზნობრივი, ჯერ გაუზომავი ბიუჯეტი: frame-ის 16.7–33 მს (60/30 fps) მხოლოდ ადგილობრივ სამუშაოს; ტექსტურ გადაწყვეტილებას backend-ში ≤1 წმ სრული round-trip-ის სამიზნე. საწყისი განაწილება: 10–30 მს state/კოდი, 100–300 მს ქსელი, 70–500 მს კომპანიის მიერ ნაჩვენები პასუხი, 10–30 მს UI — დაახლოებით 190–860 მს, არა SLA; vendor-ის end-to-end რიცხვს საკუთარი გაზომვისგან დამოუკიდებელ inference-დ არ ვთვლით. ASR დრო ცალკეა. ერთი წმ-ის deadline-ზე პასუხი დაგვიანებულად ჩაითვალოს; SDK retry-მ UI არ დაბლოკოს. `scene_version`/`step_version`-ით მოძველებული პასუხი გაუქმდეს.

On-device წესებს ქსელი და API ხარჯი არ აქვს, მაგრამ სემანტიკურ ქართულ მითითებებს ნაკლებად ფარავს. Jev-ის განხილული მიწოდება hosted API-ა ([Quick start](https://docs.typesafe.ai/introduction/quickstart)); ადგილობრივი მოდელის latency/ბატარეა მოწყობილობაზე ცალკე გასაზომია. Jev **არ წერს ნაბიჯების ტექსტს ან კოდს** ([Generation შეზღუდვა](https://docs.typesafe.ai/model-jaggedness/jev-1.13)); არ იძლევა SAM-ის კონტურებს, მუდმივ AR ID-ს ან სრულ პროცესის სისწორის დასტურს. Box-ს შეუძლია დასახელებული სამიზნის ლოკალიზაცია, მაგრამ ეს არ უდრის ყველა საჭირო უცნობი ნაწილის აღმოჩენას, ქართული label-ების შექმნასა და სანდო შეკეთების გეგმას. ცალკე vision პროტოტიპში საჭიროა ადამიანური box ანოტაციები, IoU/recall და mobile p50/p95; ტექსტური 70–500 მს სურათებზე არ გადავიტანოთ.

## 4. რისკები და მტკიცებულების ხარისხი

- **ქართული:** [Models](https://docs.typesafe.ai/models) ამბობს, რომ ინგლისური ძირითადი და საუკეთესო ენაა; სხვა ენების ხარისხი არათანაბარია. ქართული ცალკე არც მხარდაჭერის გარანტიით და არც benchmark-ით არ დასტურდება. UTF-8 მიღება ქართული სემანტიკის ცოდნის მტკიცება არ არის. საჭიროა ქართული/ინგლისური პარალელური ტესტი და ASR შეცდომები.
- **სისწორე/უსაფრთხოება:** კომპანიის [ცნობილი შეზღუდვები](https://docs.typesafe.ai/model-jaggedness/jev-1.13) მოიცავს რიცხვებს, თარიღებს, ირიბ მსჯელობას, ხმაურიან state-სა და adversarial ტექსტს. Typed პასუხი შეიძლება შინაარსობრივად მცდარი იყოს. კრიტიკული მოქმედება მარტო confidence-ზე არ უნდა დაეყრდნოს.
- **დამოუკიდებელი შეფასებები არსებობს:** [Xu/Mei, 30 სექტემბრის preprint](https://arxiv.org/abs/2610.00376) ქსელური ტრაფიკის 52,000 ჩანაწერზე Jev-ის 28.42% accuracy-ს ადარებს Random Forest-ის 69.95%-ს; 100 ჩანაწერის წყვილ შედარებაში Jev-ის median 0.750 წმ იყო. განსხვავებული supervision/service პირობებია და შედეგი „კადრზე“ არ გადმოდის. [JevAdvBench, 25 სექტემბრის preprint](https://arxiv.org/abs/2609.31142) აღწერს 812 კითხვას და state-ში დამატებული დაუდასტურებელი აზრით გადაწყვეტილებების 12.1%-ის ცვლილებას; ეს მდგრადობის შეფასებაა, არა ქართული სიზუსტის benchmark. Peer review ამ მიმოხილვით არ დადასტურებულა.
- **Privacy/vendor:** TypeSafe [აცხადებს](https://docs.typesafe.ai/models), რომ მომხმარებლის მოთხოვნებით არ წვრთნის; enterprise ZDR ცალკეა. Cloudflare-ის [Jev გვერდი](https://developers.cloudflare.com/ai/models/typesafe/jev/) ZDR-ს უთითებს — ეს არ გამორიცხავს ჩვენი backend-ის ლოგებს. გავაგზავნოთ მინიმალური state, პერსონალური ხმის/კადრის გარეშე ტექსტურ ტესტში; credentials დარჩეს backend-ზე. Preview და მოძრავი alias ზრდის ცვლილების რისკს: version pin, fallback და გადამოწმებული ზღვრები აუცილებელი დიზაინის არჩევანია.

## 5. ერთი მცირე, მოგვიანებით გასაშვები ექსპერიმენტი

**ამოცანა:** ტექსტი → არსებული ნაწილის ID ან `unknown`; vision ცდა პირველი ექსპერიმენტის ფარგლებს გარეთ დარჩეს. მონაცემის წყარო: [out_realism](../som-test/out_realism)-ში დათვლილია 49 `plan.json` / 245 ნაბიჯი, მათგან 45 C plan (13 tracking, 9 stress, 20 mini matrix და 3 pilot/visual). ეს გენერირებული გეგმებია, **არა ground truth**. კონკრეტული state-ის წყაროა [sink original plan](../som-test/out_realism/c_astra_tracking/sink/sink-trap/original/run_1/plan.json): p1 ზედა ქანჩია, p4 — მარჯვენა; ნაწილების სრული სიით უნდა შემოწმდეს შემოკლებული მაგალითები.

შევარჩიოთ 20 განსხვავებული C state; თითოეულზე ადამიანმა დაწეროს 6 ქართული მითითება (მკაფიო, სინონიმი, ASR შეცდომა, „ეს“ pointing-ის გარეშე, უხილავი ობიექტი, მსგავსი ნაწილები) და დამოუკიდებლად მონიშნოს ID/unknown. მივიღებთ 120 ქართულ და მათ 120 ინგლისურ პარალელურ შემთხვევას. პასუხი state-ში არ ჩავდოთ; `steps.focus` ეტალონად ავტომატურად არ გამოვიყენოთ. 40 შემთხვევა development, 80 held-out — **სცენით გაყოფილი**, ყველა დეგრადაცია და თარგმანი იმავე ჯგუფში. კორპუსი/ანოტაციები ამ ეტაპზე არ შექმნილა.

შედარება: (a) label/სინონიმების მარტივი წესები, (b) pin-ით Jev 1.13.0, (c) gpt-6-astra low, იმავე ტექსტური state-ითა და დახურული არჩევანით. ორივე cloud მოდელზე 240 შემთხვევა × 3 გამეორება = 720 call; ერთი call ერთ utterance-ზე, რათა batch-მა სხვა კითხვებიდან პასუხი არ გააჟონოს. არჩევანის რიგი ნაწილზე გადავურიოთ. მეტრიკები: ID accuracy, unknown precision/recall, არასწორი ავტომატური არჩევანი, abstention/coverage, ქართულსა და ინგლისურს შორის სხვაობა, განმეორებადობა, სრული p50/p95, timeout/429, input/output usage და ღირებულება სწორად გადაწყვეტილ შემთხვევაზე. Jev-ის probability-ზე Brier/ECE; Astra-ს self-reported confidence კალიბრირებულ ალბათობად არ ჩაითვალოს.

**შემოთავაზებული მიღების ზღვარი:** held-out ქართულზე ≥95% precision ავტომატურად არჩეულ ID-ებზე, ≥70% coverage, p95 ≤1 წმ და წესებზე უკეთესი coverage იმავე precision-ზე. ეს მცირე feasibility ტესტია, არა უსაფრთხოების სერტიფიკაცია; გაურკვევლობაზე დასტური დარჩება. ზღვრები development-ზე შეირჩეს და held-out-ზე აღარ მოირგოს.

**საორიენტაციო ფასი:** 720 × 2,000 input token × $0.042/1M = **$0.06048 Jev**. Astra-სთვის [ადგილობრივი vision.py-ის ტარიფი](../som-test/vision.py) input/output $10/$50 per 1M-ს ინახავს; ეს ანგარიშში **საბიუჯეტო დაშვებაა, მიმდინარე ფასის დამოუკიდებელი დადასტურება არაა**. 2,000 input და 100 billed output token/call-ზე: 720 × ($0.020+$0.005) = **$18**; ამიტომ სრული სამმაგი შედარება არსებულ $15 ზღვარში არ ეტევა. ჯერ ერთი გამეორება: 240 call/model ≈ **$6 Astra + $0.02016 Jev**; reasoning/output ზრდისა და retry-სთვის დარჩეს რეზერვი, ხოლო არსებული საერთო ledger-ის ნაშთი გადამოწმდეს. უცნობი ტარიფით ან არასაკმარისი ნაშთით არ გაეშვას. Vision-ის token რაოდენობის წინასწარი ზუსტი წესი [ჯერ არ ქვეყნდება](https://docs.typesafe.ai/images), ამიტომ ამ ტექსტურ ხარჯს Box ტესტზე ვერ გადავიტანთ.

### Vision/Box: ეტაპი 1-ის ჩანაცვლების ცალკე შემოწმება

[Box კონტრაქტით](https://docs.typesafe.ai/primitives/box), **ერთი კითხვა ერთ box-ს აბრუნებს**; ერთ სურათზე რამდენიმე დასახელებული სამიზნისთვის რამდენიმე Box კითხვა შეიძლება. `not_found` პასუხი არ არსებობს: უხილავ სამიზნეზეც box მოდის, ამიტომ თითო სამიზნეს presence-Noul უნდა ახლდეს. Label თავისუფლად არ გენერირდება: ჩვენი კატალოგიდან მივანიჭებთ ან Choice-ით ავირჩევთ. შესაბამისად, დახურული „სიფონის ნაწილების“ კატალოგი შესაძლო ჩანაცვლებაა; უცნობი სცენის ნაწილების თავისუფალი აღმოჩენა — დაუდასტურებელი.

[Image ლიმიტებია](https://docs.typesafe.ai/images): თითო განზომილება 280–1568 px, ≤16 MiB ფაილი და ≤32 MiB request. 768px thumbnail მისაღებია მხოლოდ თუ მეორე გვერდიც ≥280px-ია. ორიენტაცია წინასწარ გავასწოროთ. ფასი ითვლება image+text input token-ებზე; კონკრეტულ სურათზე ზუსტი ღირებულება უცნობია: `usage.input_tokens × 0.042 / 1,000,000`. მაგალითად, **ჰიპოთეზური** 10,000 token = $0.00042; ეს 768px ფოტოს შეფასება არ არის.

**SAM2-სთან ფორმატით თავსებადია:** [variant_b.py](../som-test/variant_b.py)-ის `box_pixels` იღებს 0–1000 XYXY-ს; ადაპტერი გადაიყვანს Jev-ს `[left,top,right,bottom] × 1000`-ად. `segment_boxes` შემდეგ pixel box-ს SAM-ს აწვდის. საჭიროა დიაპაზონის/დადებითი ფართობის შემოწმება და crop/padding-ის უკუტრანსფორმაცია. ეს კოდის მიხედვით თავსებადობის დასკვნაა, არა ხარისხის ტესტი; მცდარ სამიზნეს SAM სწორზე ვერ გადაიტანს.

ჰიბრიდის ჰიპოთეზა: **ცნობილი კატალოგი → Jev presence+Box → ID → SAM2**, პარალელურად **Astra ნაბიჯების ტექსტი** უკვე მიღებული ნაწილებით. Box-response <1 წმ სასურველი საზომია, დადასტურებული image-latency არაა; SAM-ის დრო ცალკე ემატება. თუ სამიზნეების სია ჯერ Astra-მ უნდა მოიფიქროს, მისი საწყისი დაყოვნება ისევ რჩება.

მოგვიანებითი მცირე vision ცდა: `out_realism/c_astra_tracking` და `c_astra_stress`-ის 22 დასრულებული კადრი, იმავე thumbnail-ებით/გეომეტრიით. წინასწარ დაფიქსირებული repair კატალოგი ორივე მოდელს ერთნაირად მივცეთ; არსებული Astra open-world შედეგები ცალკე ისტორიულ baseline-ად დარჩეს, თანაბარ პირობებად არ ჩაითვალოს. ახალი adapter მოგვიანებით უნდა შეიქმნას — ამ commit-ში მხოლოდ გეგმაა. გამოიყენოს [realism.py](../som-test/realism.py)-ის `mask_truth`, `match_frames`, `percentiles` და [evaluation.py](../som-test/evaluation.py)-ის `iou`/`coverage`; დიზაინის proxy-ს დაემატოს დამოუკიდებელი ადამიანური box-ები. გაიზომოს semantic target recall, box IoU, IoU≥0.5 recall, absent-target false positives, SAM mask IoU, first-box/outline p50/p95, შეცდომები და billed tokens. IoU matching იყოს one-to-one და დაკარგული სამიზნეები არ ამოვარდეს ანგარიშიდან. ტესტს steps-ის გენერაცია არ სჭირდება.

პირველად ერთი წყვილი კადრის ხარჯით შეფასდეს დარჩენილი 21 წყვილის ბიუჯეტი: `22 × (Jev საშუალო ფასი + Astra parts საშუალო ფასი)`, რეზერვით და საერთო ledger-ის ნაშთის ფარგლებში. არსებული Astra დროები ისტორიულია; ახალი თანაბარი latency შედარება მოითხოვს ახალ, მოგვიანებით ავტორიზებულ გაშვებას. **ექსპერიმენტული image/Box და უცნობი image latency ხარისხის ან სიჩქარის დაპირებას არ იძლევა.**

**შემდეგი გადაწყვეტილება:** ჯერ ქართული ID-მიბმის offline dataset და კონტროლირებული შედარება; წარმატების შემთხვევაში მხოლოდ ეს ვიწრო ფუნქცია ჩაერთოს. Vision-ის ცალკე ცდა შეამოწმებს დახურული კატალოგის ეტაპი 1-ს, არსებული Astra/SAM2/AR გეგმის წინასწარი ჩანაცვლების გარეშე.
